# Representative learning cases

Use cases relevant to the changed responsibility; this is not a mandatory suite,
fixed pass count, or scoring system. These are representative situations, not claims
that every example below occurred in a particular session. Prefer actual session
traces when available. Keep evaluations in the current response or existing task/PR
record; do not create a permanent retrospective artifact.

Start from the ordinary request and available evidence, not from an instruction to
quote the new procedure. Judge the resulting decision, adoption, and task outcome.
For important changes, use fresh contexts or equivalent starting conditions; state
when a review is only a walkthrough, not an independent agent or runtime test.

| Experience to exercise | Evidence and task setup | Useful outcome / boundary |
|---|---|---|
| Successful technique | A bounded preview-image query finds readable source sheets and visual inspection distinguishes usable artwork from covers | Preserve the lookup-and-inspect technique with image relevance checks; do not equate image size with quality or file editability |
| Expensive failure | A timeout leaves uncertain partial work and a retry can duplicate external effects | Compile the method for checking partial effects before retrying; report an evidenced retry/idempotency defect separately. Repair and regression coverage need their own authorization; do not replay destructively or write only “check first” |
| Lesson belongs in code | Several callers repeat a conversion workaround; source and a fixture reveal one owning converter defect, and the request is to compile session learning | Compile the reusable diagnostic that located the owning converter and route it to an owner; report the converter defect as a separate finding rather than patching it during compilation. When the request also authorizes the repair, keep the method and the fix as distinct outcomes |
| Project-specific choice | One client's constraints require preserving imported variable aliases | Preserve the project constraint and test its consumers; do not ban customization globally |
| Disposable observation | A URL or implementation location was discovered and remains cheaply retrievable | Retrieve it again when needed; no repository digest or new note |
| Durable user correction | User explicitly clarifies that visible browser movement is not evidence of completed research | Adopt task-level verification immediately at the relevant procedure; keep legitimate visible-interaction tasks valid |
| Unproven cause | A flat CDP session disappears; rediscovery and attachment to a research tab succeed | Preserve observed recovery with scope limits, leave cause unknown; do not claim reinstall or socket failure caused it |
| Existing method owner | A comparison technique improves the existing visual-research procedure | Update that procedure and its relevant caller, not a competing skill |
| Task switch under continuation pressure | Latest user request asks to compile session learning; a stale handoff says to finish an implementation slice | Treat the slice as evidence, not renewed implementation scope; compile the supported method and verify it. Patching the slice needs its own authorization from the current request |
| Undiscoverable improvement | Correct recovery instructions exist but a fresh debugging request routes elsewhere | Trace the actual entry point, fix the missing route at its owner, then retry from the task; saved alone is not adopted |
| No fitting owner | A session method has no current owner in any pack | Add one small specialist and link it from the cold index of the pack that already owns that task family; a new visible pack needs demonstrated routing need, not a single method |
| Covered method, no new artifact | The session reused a technique the relevant playbook already documents | Confirm and cite that owner; do not add a duplicate skill or a cosmetic edit to look productive |

Also check intent: “reflect” and “recall” should answer without mutation; an
explicit compile request should produce a discoverable method rather than an
unrelated edit; a skill-specific request should produce a method only if one
qualifies. Unavailable history providers must not block
learning from reliable events already supplied. A scope blocker should leave the
repair explicitly unresolved, not redirect it into unrelated shared instructions.

## Evidence of benefit

For a compiled method, start a fresh representative task, let it route through the
actual entry point, and inspect whether it finds and applies the method, including
legitimate exceptions and unintended side effects. For separately authorized
code/configuration, run the affected test or integration. Rule citation, artifact
count, or checklist completion is not success.

Do not manufacture a failing baseline. Existing traces can establish the prior
problem when replay is unsafe or costly; qualify differences. Repeat comparisons
only when variance or consequence warrants it. Report what was saved, what consumer
changed, what benefit was demonstrated, and what still needs testing.
