# Diagnose an underused MCP capability

Use when an agent skips a configured tool, or workflow guidance recommends a tool
that its live description restricts. Diagnose the missing task outcome, not the
call count. A known-file lookup may legitimately need no delegation.

## Trace the failing layer

1. **Specify the expected job.** Choose one representative question and the
   evidence a useful answer would return. Separate failure to select a tool from
   failure to connect, execute, or obtain relevant source.
2. **Check the live contract and connection separately.** Discover the tool and
   inspect its description, arguments and permissions. Make a harmless authorized
   read through the actual host route. A successful repository listing proves
   retrieval connectivity, not permission or readiness for delegated research;
   model registration likewise does not prove a model call works. Continue with
   permitted retrieval while a different capability is blocked.
3. **Locate the restriction's owner.** Trace the relevant path from the deployed
   server's tool registration through transport discovery and host descriptor
   construction to the effective prompt. Inspect narrow source ranges and tests
   where a boundary is uncertain; compare the deployed version, not only upstream
   main. Read configuration schemas before proposing settings. A server description
   is not necessarily a tool-description override, and editing workflow prose
   cannot change a compiled server descriptor. Avoid full configuration dumps;
   extract only safe fields and keep credentials out of output.
4. **Check adoption by content.** Verify which instructions the host actually
   receives, including resolved links, copies and loaded descriptor caches. A
   template's existence does not show it was invoked, and an explicit-request gate
   is satisfied only by the instruction in effect, never by a template that merely
   exists. Follow the live permission contract and the owning playbook's stated
   condition. If the intended guidance already reaches the host, adding another
   rule is unlikely to fix a lower-layer conflict.
5. **Check evidence coverage independently.** Read pagination totals or query the
   exact repository rather than counting one result page. Confirm the relevant
   branch and local changes. For indexed source, follow the
   [coverage and freshness procedure](../../cross-repo-source/README.md#verification-and-freshness):
   connectivity and a recent timestamp do not establish current code truth.
6. **Choose the smallest supported repair.** Change the failing owner, not a
   neighboring description or an invented override. If no supported setting
   exists, state whether a source change and deployment are needed, including
   interruption, rollback and authorization boundaries. Do not quietly insert a
   proxy, modify installed bundles, or relabel a documentation edit as a runtime
   fix. Keep a blocked repair distinct from any reusable guidance adopted.

## Verify the outcome

After an authorized change, refresh the appropriate host connection/cache and
inspect the effective descriptor again. Exercise the representative task through
that route, then check its decisive source evidence. Keep configuration validity,
metadata propagation, successful execution and useful task output separate.

Also try a legitimate exception: a narrow lookup should remain direct, and a
restricted tool should remain unused without the required authorization. A
successful diagnostic trace establishes a usable method, not proof that it caused
past omissions or that the proposed repair works. Claim reduced cost or improved
selection only after a comparable behavioral test.
