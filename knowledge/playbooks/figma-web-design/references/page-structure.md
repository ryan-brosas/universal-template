# File, page, and layer organization

The source course treats organization as the highest-priority habit, because messy layer and page trees slow every later operation.

## Files

- Label every file; untitled files become unidentifiable quickly.
- Pin the files in active use so they stay reachable without scrolling a long drafts list.
- Group related files with a consistent numeric prefix so an alphabetical sort clusters them (for example icon sets, UI kits, wireframe kits).
- Group by purpose rather than by client where possible, so reusable material is findable.
- Identify unused files, but obtain approval before deleting user or shared
  material; organization work is not deletion permission.

## Pages

Preserve the approved source structure. For an explicitly authorized new
blueprint, the course offers this example page skeleton:

1. **Cover** - thumbnail-facing, worth designing since it represents the file.
2. **Brand guide** - colours and typography, reachable at a glance.
3. **Design system** - tokens, styles, components, layout starters.
4. **Wireframes** - break the page further when a project has many screens.
5. **High fidelity** - the pixel-accurate designs actually built from.
6. **Components** - the component library.
7. **Graphics** - illustrations and imagery.

Create only pages needed for the task. Reuse existing covers and other visual
assets; do not design them merely because this example lists them. Confirm
content and dependencies before proposing removal of a page.

## Layers

- Name layers as you build rather than tidying in bulk later.
- Keep layer order matching visual order.
- Prefer grouping content over long flat lists, and frame sections that will become auto-layout containers.

## Blueprint

A blueprint is an approved project starter containing layout styles, tokens
and components. Reuse or duplicate it as permitted, preserve source links and
bindings, and adjust only the authorized content and properties.
