# gRPC parallel route registry — how do structured {service, rpc, streaming} routes map onto a flat handler map without the canonical pattern normalizer?

**Source:** nest (MIT) `master@4c38a5ab100f`; Codebase Memory `nest`. **Question:** When your routing keys are structured objects (service + method + streaming type) instead of arbitrary patterns, do you normalize them like every other transport, or run an exact-string registry — and what breaks if you mix the two?

## Two registry conventions in one codebase
**Path/Symbol:** `packages/microservices/server/server-grpc.ts:ServerGrpc.addHandler` (575-583), `ServerGrpc.createPattern` (245-255), `ServerGrpc.getMessageHandler` (221-235); contrast base `packages/microservices/server/server.ts:addHandler/getHandlerByPattern/getRouteFromPattern` (139-159, 165-170, 337-347).
**Signature:** `addHandler(pattern: unknown, callback: MessageHandler, isEventHandler = false)`; `createPattern(service: string, methodName: string, streaming: GrpcMethodStreamingType): string`.
**Data Shape:** `messageHandlers: Map<string, MessageHandler>`; gRPC keys are raw `JSON.stringify(pattern)` strings; base-transport keys are canonical sorted-key routes from `transformPatternToRoute`.

### Decisive source
```ts
// base Server — registration normalizes, lookup re-parses then normalizes:
public addHandler(pattern: any, callback: MessageHandler, ...) {
  const normalizedPattern = this.normalizePattern(pattern);   // transformPatternToRoute
  ...
  this.messageHandlers.set(normalizedPattern, callback);
}
public getHandlerByPattern(pattern: string): MessageHandler | null {
  const route = this.getRouteFromPattern(pattern);            // JSON.parse → normalizePattern
  return this.messageHandlers.has(route) ? this.messageHandlers.get(route)! : null;
}

// ServerGrpc — BOTH ends overridden, exact JSON strings, no normalizer:
public addHandler(pattern: unknown, callback: MessageHandler, isEventHandler = false) {
  const route = isString(pattern) ? pattern : JSON.stringify(pattern);
  callback.isEventHandler = isEventHandler;
  this.messageHandlers.set(route, callback);                  // no tail-append chain either
}
public createPattern(service: string, methodName: string, streaming: GrpcMethodStreamingType): string {
  return JSON.stringify({ service, rpc: methodName, streaming });
}
```

**Flow:** proto load → for each namespaced service (`A.C.E` dot-names via collectDeepServices) → createService walks prototype methods → handler lookup tries `{service, rpc, streaming}` key with the CONFIGURED service name, falls back to the fully-qualified name from `grpcMethod.path.split('/')[1]` (`/package.example.test/TestMethod` → `package.example.test`), else skips the method → registered handlers are wrapped by the streaming adapter selected from the native handler's booleans (requestStream+RX→createRequestStreamMethod, requestStream+PT→createStreamCallMethod, responseStream→createStreamServiceMethod, else unary). For a requestStream method the RX pattern is tried FIRST and PT only if RX missed.
**Invariant:** the two registries never interoperate — a gRPC handler registered under `JSON.stringify({service,rpc,streaming})` is invisible to `getRouteFromPattern` lookups and vice versa; the streaming TYPE is part of the key, so `@GrpcMethod` and `@GrpcStreamMethod` on the same method name are distinct routes; duplicate gRPC patterns overwrite (no event-chain append — that lives only in the base addHandler).
**Probe:** `packages/microservices/test/server/server-grpc.spec.ts` (addHandler asserts `set` called with `JSON.stringify(pattern)`; createPattern equals `JSON.stringify({service, rpc, streaming})`; getMessageHandler resolves via configured name, via `path.split('/')[1]`, and returns undefined for unknown methods; createService pins RX-first/PT-fallback call order).
**Runner caveat:** repo deps uninstalled (vitest blocked); expectations quoted from spec source read directly.

## Verdict
Adopt "structured keys ⇒ exact-string registry" as a deliberate alternative to canonical normalization when keys carry non-pattern dimensions (streaming mode) and both writer and reader are generated by the same code — it removes normalization cost and collision risk entirely; adopt the base pair (`register-normalize / parse-then-normalize lookup`) when patterns cross a wire from untrusted producers. Adapt the path-split fallback to however your RPC framework exposes fully-qualified method paths. Omit gRPC's overwrite-only semantics if you need fan-out on one key — reuse the base event-chain instead.
