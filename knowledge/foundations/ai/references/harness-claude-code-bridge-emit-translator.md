# Claude-code bridge emit translator — how do you manufacture well-formed steps and blocks from an SDK that streams content-block indices, not stable part ids?

**Source:** Vercel AI SDK Apache-2.0 `main@9d9a73f1551f2243035491e9de5a2e00ebf9eb17`; Codebase Memory `ai`. **Question:** The Claude Agent SDK reports partial text as `content_block_start/delta/stop` keyed by a per-message block INDEX (no stable id), tool calls as assistant `tool_use` blocks whose results arrive later as user `tool_result` blocks carrying only the id, and subagent traffic interleaved with parent traffic — how does the bridge emit exactly one well-formed text/reasoning/tool/step sequence?

## Partial-block state machine keyed by content-block index
**Path/Symbol:** `packages/harness-claude-code/src/bridge/create-emit-stream-event.ts` — `createEmitStreamEvent` (:95–302), `handleStreamEvent` (:374–429), `ClaudeStreamEventState` (:50–75), `createClaudeStreamEventState` (:77–91); step machinery `finishApprovalStep` (:304–316), `emitFinishStep` (:318–336), `closeStepIfReady` (:338–353); usage `mapUsage` (:453–476), `defaultUsage` (:478–483); helpers `stringifyContent` (:431–443), `parseMcpToolResult` (:445–451), `formatApiRetryWarning` (:355–372).
**Signature:** `createEmitStreamEvent({ state, emit, emitWarning, emitTerminalError, onCompactionBoundary, toCommonName }): (event: ClaudeMessage) => void`.
**Data Shape:** `partialBlocks: Map<number, { id: string; kind: 'text' | 'thinking' }>`. On `content_block_start` a randomUUID id is minted and `text-start`/`reasoning-start` emitted; deltas route ONLY when block kind matches delta type (`text_delta`→text-delta, `thinking_delta`→reasoning-delta); `content_block_stop` deletes the entry and emits the matching end. Unknown indices are dropped silently (a delta before its start emits nothing).

**Flow:** every message first passes the once-only stream-start (carrying modelId when the message is system/init with a string model) → api_retry classification (401/403/404 ⇒ terminal error `HTTP <status>: <error>`; other statuses ⇒ formatted warning `Claude Code API retry: attempt N/M; HTTP S; retrying in Dms; <error>`) → terminal-error observation (any non-empty msg.error is remembered for the empty-success re-emit) → auth_status error / task_updated-failed patch ⇒ immediate terminal error → compact_boundary ⇒ onCompactionBoundary (trigger + numeric-only token fields) and RETURN → subagent gate (`parent_tool_use_id != null` drops the whole message, including partial stream events) → stream_event ⇒ partial-block machine → assistant ⇒ tool_use classification → user ⇒ tool_result resolution + closeStepIfReady. Tool_use classification ladder: `StructuredOutput` name ⇒ id recorded in structuredOutputToolUseIds and skipped (the internal structured-output tool never surfaces); `mcp__harness-tools__*` prefix ⇒ id added to BOTH mcpToolUseIds and pendingStepToolUseIds and opensStep=true but NO emission (the MCP handler already emitted its own pair with the user-facing name); otherwise record nativeName, mark dynamic for any `mcp__` prefix (external MCP servers), skip if approval-requested, else emit providerExecuted:true. Tool_result resolution mirrors it: structured-output ids deleted-and-skipped; harness-tools ids deleted from both sets and skipped; everything else resolves the native name from the map (fallback 'unknown'), emits tool-result with isError, and deletes the pending id. Result shaping: bash results become `{exitCode: isError ? 1 : 0, stdout: content}` (the SDK exposes no real exit code — documented stand-in for Codex's native shape); dynamic MCP results pass through parseMcpToolResult (JSON.parse with string fallback); others use stringifyContent (string passthrough / array-of-text join / JSON fallback).
**Invariant:** consumers never see unclosed or duplicated blocks — every start has exactly one end because both ride the same map entry; a step's finish-step lands ONLY after all its tool results AND all its partial blocks have closed (closeStepIfReady triple gate), so step boundaries always contain complete tool round-trips; each gated tool produces exactly one tool-call across canUseTool + assistant block combined (approvalRequestedToolUseIds is the dedup channel); subagent traffic (parent_tool_use_id set) can never open, close, or pollute a parent step; mapUsage folds cache tokens into input total (total = input + cache_creation + cache_read; noCache = input only) so V4-style nested counters stay honest.

## Verdict
Adopt the index-keyed partial-block map for any runtime that streams content blocks by position rather than by stable id (mint your own id at start, route deltas by stored kind, delete at stop); adopt the triple-gate step closure (stepOpen && no pending tool ids && no open partials) whenever steps must contain complete tool round-trips; adopt the suppression-ladder pattern for tools announced through two channels (record the announcing channel's ids, skip the echo channel); adopt the bash exitCode synthesis only when your consumer contract demands a numeric exit field and the runtime cannot provide one — document it as a stand-in; adapt the api_retry status split (auth-class statuses terminal, transient ones warnings) to your provider's semantics; omit the whole translator where the runtime already emits stable part ids (opencode parts, ACP updates).
