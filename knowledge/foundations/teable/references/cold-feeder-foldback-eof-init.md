**Source:** teable `bucket-merge-feeder.ts` @ pin `06a4461e`
**Question:** Why fold existing parts back in via full external sort instead of streaming merge or clobber?
**Path/Symbol:** `BucketMergeFeeder {writer, existingParts, coldStorage, sorter}`, `push(row)`, `finish()`, `abort()`, `consumedKeys`, `ensureInitialized()`
**Signature:** lazily on FIRST push (or finish): reads every existing part to EOF into the sorter, THEN buffer rows join; drain emits the deduplicated byte-ordered union into the PartWriter.
**Decisive source:** :8-27 rationale — (1) a bucket flushes more than once with disjoint row sets so "existing parts must be folded back in — never clobbered"; (2) "NO input order can be trusted: the buffer stream follows the db collation, which orders mixed-case cuids differently than the byte comparator ... (a streaming merge under mismatched orders silently emits duplicates)"; (3) "each existing part is read to EOF immediately (short-lived GET) — dozens of half-open download streams interleaved with uploads on one HTTP client deadlock it".
**Flow/Invariant:** `consumedKeys` = exactly the pre-existing keys this feeder read — "the only keys a heal pass may delete afterwards (a key that appeared concurrently belongs to another run and must survive)" (:54-61). Existing-part rows are healed through `truncateColdRow` on read-back when truncation is configured. `abort()` releases budget charge/temp files/registry WITHOUT emitting — idempotent; for tables dying between feeder open and finish loop. `mergedExistingRows` counts folded rows separately from flushed buffer rows.
**Probe (direct test):** spec "re-flushing a bucket merges its existing parts instead of clobbering them" (5 existing + 2 new incl. one overlap dup → all 7 decoded once); live: `grep -c 'initialized' apps/nestjs-backend/src/features/record-history-cold/bucket-merge-feeder.ts` → `3`; `grep -c 'mergedExistingRows' ...` → `2`.
