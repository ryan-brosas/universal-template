# Initial doc SQL bootstrap — how is an empty document's schema born, and what does the generator's output pin down?

**Source:** grist-core (Apache-2.0), `main@b83224bbe9c88910dfeb28922df254a26f702f68`; Codebase Memory `grist-core`. **Question:** What exactly must be true of the seed SQL that creates a fresh Grist document, and why is it generated rather than written?

## initialDocSql generated bootstrap
**Path/Symbol:** `app/server/lib/initialDocSql.ts:GRIST_DOC_SQL` (5-41), `GRIST_DOC_WITH_TABLE1_SQL` (43-100); generator at `app/server/generateInitialDocSql.ts`.
**Signature:** `export const GRIST_DOC_SQL: string` / `export const GRIST_DOC_WITH_TABLE1_SQL: string` — each a single multi-statement script (`PRAGMA foreign_keys=OFF; BEGIN TRANSACTION; ... COMMIT;`) executed via `exec()` on document creation.
**Data Shape:** ~24 `_grist_*` tables, every non-key column declared with an explicit `DEFAULT` (`''`/0/NULL), ordering columns typed `NUMERIC DEFAULT 1e999` (parentPos/pagePos/tabPos/rulePos/manualSort). Seed rows: `_grist_DocInfo` schemaVersion **46**; ACL bootstrap rows — one `_grist_ACLRules(id=1, resource=1, permissions=63, principals='[1]')`, `_grist_ACLResources(id=1,'','')`, four `_grist_ACLPrincipals` groups (Owners/Admins/Editors/Viewers). The WITH_TABLE1 variant adds a demo table `Table1(A,B,C BLOB)` plus its raw-data view/sections/fields wiring.

```sql
INSERT INTO _grist_DocInfo VALUES(1,'','','',46,'','');
INSERT INTO _grist_ACLRules VALUES(1,1,63,'[1]','',0,'','',1e999,'','');
-- user data columns are typeless BLOBs; typing lives in metadata:
CREATE TABLE IF NOT EXISTS "Table1" (id INTEGER PRIMARY KEY,
  "manualSort" NUMERIC DEFAULT 1e999, "A" BLOB DEFAULT NULL, ...);
```

**Flow:** DocStorage's `createFile`/initialization executes one variant whole inside its own transaction. The file header says it plainly: `THIS FILE IS AUTO-GENERATED BY app/server/generateInitialDocSql.ts` — the generator renders the schema from the same code-level schema definitions used by migrations, so hand-edits here would silently drift from the migration chain. The WITH_TABLE1 variant exists so tests/diffs have a canonical non-empty document.
**Invariant:** Position columns default to `1e999` (IEEE infinity) so new rows sort AFTER all existing rows without any backfill — a porter replacing this with MAX_INT changes tie-breaking semantics. User-table value columns are ALWAYS `BLOB DEFAULT NULL` regardless of logical type: dynamic typing is enforced by the affinity-safe encoder (see sqlite-value-affinity-encoding), not by SQL types. `PRAGMA foreign_keys=OFF` + explicit transaction wrap the whole script; schemaVersion 46 in the seed row is what triggers the migration ladder on next open. Treat this file as build output: regenerate, never edit.
**Probe:** No dedicated unit test for the constants themselves (coverage caveat); they are exercised by every suite that creates a fresh document (e.g. `test/server/lib/DocStorage.js`). Deterministic anchors: `grep -c "1e999" app/server/lib/initialDocSql.ts` → 6+ hits; `grep -n "AUTO-GENERATED" app/server/lib/initialDocSql.ts` → :2.

## Verdict
Adopt the generated-single-script bootstrap shape, infinity-default ordering, typeless-BLOB value columns, and ACL seed rows as the empty-document contract; adapt table set to your schema version; omit nothing structural if porting Grist documents — but regenerate from your own generator rather than copying the artifact.
